# `battery_state` module

This module ships two nodes that together produce a `sensor_msgs/BatteryState`
stream on `platform/bms/state` for every supported Clearpath platform.

| Node | Purpose |
| ---- | ------- |
| `battery_state_estimator` | Estimates `BatteryState` for **non-smart batteries** that cannot report their own state. Subscribes to `platform/mcu/status/power` and derives voltage, current, percentage, status, etc. from the MCU's `Power` message. |
| `battery_state_control`   | Higher-level controller (e.g. low-SoC actions, charger handoff). Not described in this README. |

The remainder of this document covers only `battery_state_estimator`.

## When to use it

Use `battery_state_estimator` for any pack that the MCU exposes as raw
**voltage + current** measurements but which has no internal BMS able to
report SoC, health, temperature, cell voltages, etc. Typical examples are
sealed lead-acid (VRLA) packs and basic LiFePO4 packs without a smart BMS.

Do **not** use this node for batteries that ship their own `BatteryState`
publisher (smart packs, CAN-BMS packs, etc.). Those publish a fully populated
`BatteryState` directly and bypass this estimator entirely.

## Data flow

```
Platform MCU ──Power──▶ /platform/mcu/status/power
                                  │
                                  ▼
                     battery_state_estimator
                                  │
                                  ▼
                       /platform/bms/state  (sensor_msgs/BatteryState)
```

### Why `Power` is platform-aware

Clearpath uses a **single `clearpath_platform_msgs/Power` message** to report
voltage and current readings for every platform — A200, J100, W200, DD100/DO100,
DD150/DO150, R100, etc. — because they all share the same MCU framework.

But platforms differ in how many sources/channels they expose and which
`measured_voltages[]` / `measured_currents[]` index corresponds to the
**battery pack**. For example, A200's pack voltage lives at
`Power.A200_BATTERY_VOLTAGE`, and its pack current is the sum of the MCU/user
port current, left driver current and right driver current. J100, by contrast,
exposes a single battery voltage at `Power.J100_MEASURED_BATTERY` and a single
`Power.J100_TOTAL_CURRENT`.

To know which fields to read, the node must be told which platform is
publishing the message. That is the purpose of the `platform` parameter — it
selects a small per-platform layout (`initialize_platform_enums`) that
maps `Power` indices to "pack voltage" and "pack current contributions".

### Estimator math (per incoming `Power` message)

1. Read `pack_voltage = measured_voltages[<platform_voltage_index>]`.
2. Read `pack_current = sum(measured_currents[i] for i in <platform_current_indices>)`.
3. Append `pack_voltage` to a rolling buffer of size `rolling_average_window`.
4. Interpolate `percentage` from the scaled voltage→percentage lookup table
   using the rolling-average voltage (clamped at table extremes).
5. `status = CHARGING` if `Power.charger_connected` else `DISCHARGING`. If
   charging and `percentage == 1.0`, promote to `FULL`.
6. Populate cell-voltage array as `[pack_voltage / num_series] * (num_series * num_parallel)`.
7. Publish on `platform/bms/state`.

### Configuration

Per-battery shipped configs live under
`clearpath_hardware_interfaces/config/battery_state_estimator/<battery>.yaml`
and define the LUT, per-unit capacity / voltage, and the
`sensor_msgs/BatteryState.power_supply_technology` enum index. The launch
file generated by `clearpath_generator_robot` overlays the per-robot pack
geometry (`platform`, `cell.num_series`, `cell.num_parallel`) on top of the
shipped config.

#### Parameters

All parameters live under the `/**: { ros__parameters: ... }` wildcard key
so the same yaml works regardless of node name or namespace.

| Parameter | Type | Default | Description |
| --- | --- | --- | --- |
| `technology` | `int` | `0` | `sensor_msgs/BatteryState.power_supply_technology` enum index. Copied verbatim onto every published `BatteryState`. Common values: `0` UNKNOWN, `2` LION, `3` LIPO, `4` LIFE, `8` VRLA. |
| `cell.voltage` | `float` (V) | `0.0` | Nominal voltage of **one battery unit** (a single physical pack, not a single electrochemical cell). Used for sanity / display. |
| `cell.capacity` | `float` (Ah) | `0.0` | Capacity of **one battery unit** in amp-hours. The node publishes `capacity = num_parallel * cell.capacity` and `charge = capacity * percentage`. |
| `cell.num_series` | `int` | `1` | Number of units wired in series in the deployed pack. Multiplies the LUT voltages so interpolation runs on pack voltage instead of per-unit voltage, and sets the length of the `cell_voltage[]` array (`num_series * num_parallel`, each entry = `pack_voltage / num_series`). |
| `cell.num_parallel` | `int` | `1` | Number of units wired in parallel in the deployed pack. Multiplies `cell.capacity` to give the published pack capacity. |
| `lookup_table.voltages` | `list[float]` (V) | _required_ | Per-unit voltage breakpoints, strictly monotonic ascending. Same length as `lookup_table.percentages`. Scaled by `num_series` at startup. |
| `lookup_table.percentages` | `list[float]` (0..1) | _required_ | State-of-charge percentages corresponding to each entry in `lookup_table.voltages`. Must be non-decreasing, start at `0.0` and end at `1.0`. |
| `rolling_average_window` | `int` | `30` | Number of most-recent `Power` messages whose pack voltages are averaged before LUT lookup. Larger window = smoother percentage but slower response. |
| `platform` | `str` | `'a200'` | Selects the per-platform `Power` index layout. Must be one of `a200`, `j100`, `w200`, `dd100`, `do100`, `dd150`, `do150`, `r100`. Usually injected by the generated launch file from the robot's `serial_number`. |

A note on "cell": the node treats one **battery unit** (e.g. one 12 V SLA
pack) as a "cell". This matches how Clearpath wires multi-pack systems
(e.g. two 12 V units in series = a `S2P1` 24 V configuration), but it does
**not** mean electrochemical cells.

#### Defining a new battery

A new battery only requires one yaml file under
`config/battery_state_estimator/`. Use an existing config (such as
[es20_12c.yaml](../../config/battery_state_estimator/es20_12c.yaml)) as a
template:

```yaml
# Example: 12 V 20 Ah sealed lead-acid pack
/**:
  ros__parameters:
    technology: 8                      # VRLA
    cell:
      voltage: 12.0                    # one pack is 12 V nominal
      capacity: 20.0                   # one pack is 20 Ah
      # num_series / num_parallel are overlaid by the generated launch.
    lookup_table:
      voltages:    [11.60, 11.90, 12.20, 12.40, 12.55, 12.70]
      percentages: [ 0.00,  0.20,  0.40,  0.60,  0.80,  1.00]
```

Rules of thumb:

* Express the LUT in **per-unit** volts (the per-pack nominal `cell.voltage`).
  The node scales by `num_series` at startup, so the same yaml works for
  `S1P1`, `S2P1`, `S4P3`, etc.
* The first LUT percentage must be `0.0` and the last must be `1.0`. The
  node will refuse to start otherwise.
* Do **not** set `platform`, `cell.num_series`, `cell.num_parallel`, or
  `rolling_average_window` in this file. Those are overlaid per-robot by the
  generated launch from the user's `robot.yaml` battery configuration; if
  you hard-code them here you'll cause the override to look like a "matching
  override" and emit confusing log noise (or, for `platform`, ship a
  per-platform default into every robot).
* Pick `technology` from the `sensor_msgs/BatteryState` enum, not from any
  Clearpath-internal name list.

Once the yaml is in place, register the battery model in
`clearpath_config.common.types.platform`'s `VALID_BATTERIES` for every
platform that should accept it, and add a mapping in
`test/test_node_parity.py`'s `BATTERY_TO_CONFIG_FILE` plus a sweep in
`test/tools/generate_inputs.py`. See [test/README.md](test/README.md) for
the test wiring steps.
